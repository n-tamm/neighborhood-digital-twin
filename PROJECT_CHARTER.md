# Project Charter

This document is the canonical description of the project. The original brainstorming document and the longer capstone proposal remain useful background, but this charter controls current scope when those drafts differ.

## Project statement

Most public housing tools either describe current conditions or forecast a single outcome at a broad regional level. This project asks whether public housing, demographic, economic, geographic, development, environmental, and spatial data can support a richer longitudinal representation of U.S. census-tract communities.

The work will produce a reproducible tract-year data system, forecast housing-market trajectories over several horizons, estimate uncertainty, measure the value of spatial context, and identify earlier community states that resemble a selected neighborhood today. Those results will be delivered through a map-driven Neighborhood Digital Twin where users can explore history, forecasts, comparisons, historical analogues, and carefully bounded scenarios.

## Primary research question

Can heterogeneous public data support useful, transferable, interpretable, and uncertainty-aware models of neighborhood trajectories, and can those models power a credible interactive Neighborhood Digital Twin?

## Supporting questions

1. How accurately can housing-market trajectories be forecast over one, three, and—where defensible—five years using only information available at the forecast date?
2. Do neighboring-tract and metropolitan conditions improve forecasts after accounting for a tract's own history?
3. How well does the model generalize to later years and to metropolitan areas omitted from training?
4. Are uncertainty intervals calibrated across places, market regimes, and levels of source coverage?
5. Which feature families add useful out-of-time information beyond housing momentum and regional conditions?
6. Can a compact neighborhood representation retrieve historical tract-years whose later paths are informative?
7. Can a bounded scenario engine show meaningful model sensitivity without implying causal policy effects?
8. Can an interactive application make these results understandable without encouraging neighborhood ranking or investment overclaims?

## Unit of analysis and initial target

The intended analytical unit is a census tract represented on a canonical 2020 tract geography. The main table will contain one record per tract and forecast origin year, with source vintages and quality flags retained.

The initial prediction target is future change in the FHFA tract-level House Price Index. One-year forecasting is the primary evaluation target. Three-year and five-year targets are added only if the feasibility audit leaves enough independent forecast origins and acceptable coverage.

The HPI is a market indicator, not a complete description of a community. The application will place it beside affordability, housing burden, vacancy, supply, population, income, and other contextual measures.

## Required minimum product

The capstone MVP includes:

- a reproducible bronze, silver, and gold public-data pipeline;
- a canonical tract-year neighborhood-state table with lineage and data-quality flags;
- a documented release-date and geography-alignment policy;
- persistence, regional, and regularized-linear baselines;
- one justified nonlinear forecasting model;
- time-based backtesting and at least one geographic holdout;
- calibrated forecast intervals and performance slices;
- a with/without-spatial-context comparison;
- a simple and evaluated historical-analogue method;
- a scenario engine with two to four supported inputs, bounded ranges, and out-of-distribution warnings;
- a deployed map-driven application for selected demonstration metros;
- at least three original visuals generated by code;
- a final report, model card, data statement, ethics discussion, and demonstration artifact.

## Valuable extensions

These additions are welcome only after the MVP works end to end:

- trajectory clustering with stability analysis;
- learned embeddings that outperform simpler representations on a stated task;
- county or metro building-permit and employment context;
- environmental-risk or accessibility layers;
- correlated or conditional scenario simulation;
- wider national application coverage;
- a natural-language interface that queries the project's actual outputs.

## Explicit non-goals

The project will not:

- estimate individual property values;
- scrape or depend on proprietary transaction data;
- claim that changing an input causes a forecasted outcome;
- recommend buying, selling, or investing in a location;
- create a single neighborhood quality score;
- predict demographic composition;
- require user accounts or collect precise personal locations;
- build a large microservice architecture before the research question is answered.

## Evidence standard

Every model result should answer four questions:

1. What information was available at the prediction date?
2. What simple baseline did the method need to beat?
3. How does performance change across time, geography, and data quality?
4. What uncertainty or limitation should a user see beside the result?

Random row splits are not acceptable for the main evaluation. Preprocessing, feature selection, and calibration must be fitted on training data only. The latest locked test period is used once the approach is frozen.

## Product principles

- Put the baseline beside the machine-learning result.
- Give uncertainty the same visual weight as the point forecast.
- Show source coverage and missingness for the selected tract.
- Describe model drivers as associations, not causes.
- Keep scenario assumptions and plausibility limits visible.
- Avoid color scales or labels that imply moral quality.
- Make methods and definitions available without forcing every user to read them first.
- Keep a recorded or static fallback in case a free hosting service is unavailable.

## Definition of done

The project is complete when:

- a new contributor can reproduce a small end-to-end run from documented commands;
- every source has a URL, vintage, access note, checksum or equivalent identifier, and citation;
- every feature is available at the stated forecast date;
- geography matching, row attrition, and coverage bias are documented;
- the final evaluation includes strong baselines, a locked time test, a geographic holdout, and uncertainty coverage;
- the analogue and scenario components have explicit evaluation rather than only visual demonstrations;
- the public app integrates current state, history, forecasts, uncertainty, drivers, comparisons, analogues, and scenario sensitivity;
- the model card and ethics discussion identify likely misuse and affected groups;
- at least three original figures are generated by code;
- all required capstone deliverables have a named owner and completion check.

## Scope decisions

Five gates keep the project from expanding faster than it can be validated:

1. **Geography feasibility:** national tracts, selected metros, or county fallback.
2. **Neighborhood-state contract:** freeze the core dimensions and defer low-value sources.
3. **Forecast model:** select a champion and stop algorithm shopping.
4. **Digital Twin core:** accept the scenario engine only after support and stability tests pass.
5. **Content freeze:** after final evaluation, allow only defect fixes, clarity work, and required deliverables.

Changes to the MVP, target, geography, or deployment architecture should be recorded in `docs/decisions/` so the reason does not disappear into chat or notebook history.
